## Подход и границы первого релиза

Предлагаемый путь — Capacitor с локально упакованной сборкой Vite и существующим удалённым API. Сохраняем учебную логику, контент и общий код веб-приложения. Нативные возможности подключаем через отдельные адаптеры платформы. Release-сборка не должна зависеть от dev server или загружать весь интерфейс с production сайта.

Первый релиз: регистрация и вход, onboarding, уроки, словарь, практика, прогресс, профиль, настройки и подписка Plus. Учительский и административный интерфейсы остаются веб-инструментами; права API продолжают проверяться на сервере. Полный offline-каталог и новые учебные функции не являются условием первого выпуска. Сохранность уже реализованной очереди прогресса — обязательна.

## 1. Подготовить воспроизводимую основу

- Создать отдельную ветку для iOS. Не включать существующие локальные правки в коммиты миграции без отдельного просмотра.
- Проверить установку по lockfile и повторить build/tests; зафиксировать поддерживаемые версии Node, Capacitor, Xcode и минимальную iOS по выбранной версии Capacitor.
- Добавить Capacitor, конфигурацию с `webDir: dist`, iOS-проект и команды build/sync/open.
- Выбрать Bundle ID до создания записи App Store; кандидат `sk.slovakgo.app` требует проверки доступности и согласования с Apple Team.
- Сделать настройки API отдельными для native staging и production. Исключить серверные секреты, веб-сборки и временные файлы из iOS-артефакта.
- Проверить маршруты и обновление экрана; отключить веб service worker и установочные PWA-подсказки внутри native приложения.

Готово, когда: чистая сборка запускается в iOS Simulator из упакованных ресурсов; API ping работает; веб-приложение продолжает собираться.

## 2. Обеспечить вход и сохранность данных

Критическая зависимость: `apiClient.ts` использует относительный `/api`, `credentials: include`, а сервер выдаёт HttpOnly cookie с `SameSite=Lax`. CORS сейчас не содержит native origin. Простого добавления адреса API недостаточно для доказательства работоспособности входа в WKWebView.

- Сначала проверить на устройстве стратегию сессии: нативный HTTP/cookie transport либо отдельная серверная сессия с безопасным хранением в Keychain. Не ослаблять веб-защиту ради WebView.
- Добавить только требуемые native origins и проверить preflight, авторизацию, logout и истечение сессии.
- Адаптировать Google OAuth: системная авторизация, безопасный callback/deep link, проверка state и передача сессии. Сейчас вход использует переход на `/api/auth/google/start` и возврат на веб-страницу.
- Для сохранённого Google-входа добавить Sign in with Apple как путь выполнения требований 4.8; обработать скрытый email, связывание аккаунтов без потери прогресса и отзыв авторизации.
- Проверить регистрацию, восстановление пароля, вход после перезапуска и переключение аккаунтов.
- Сохранить изоляцию offline-очереди по пользователю, отправку после восстановления сети и отсутствие повторного начисления XP.
- Проверить существующее удаление аккаунта: UI и `/auth/delete` уже реализованы. Проверить связанные данные, очистку локального хранилища, Apple login и поведение активной Apple-подписки; поправить устаревшие переводы.

Готово, когда: новый и существующий пользователь проходят вход → урок → перезапуск → восстановление прогресса; logout, смена аккаунта и удаление не оставляют доступ к чужим данным.

## 3. Подключить подписки App Store

Обновление от 3 ноября 2026: StoreKit 2, серверная проверка и уведомления App Store реализованы на ветке `feat/ios-in-app-purchases`. Настройка App Store Connect и проверка описаны в [IOS-PURCHASES.md](IOS-PURCHASES.md).

Сейчас paywall, shop и управление подпиской перенаправляют в Stripe. Для первого iOS-релиза планируем стандартный In-App Purchase для цифрового Plus; региональные программы внешних платежей не входят в этот план.

- Ввести общий billing-интерфейс: веб использует Stripe, iOS — StoreKit через поддерживаемую интеграцию. Сравнить прямую интеграцию и RevenueCat до выбора зависимости.
- Создать месячный и годовой продукты, subscription group и локализации в App Store Connect. Проверить цену и доступность trial; не переносить автоматически обещание веб-trial в iOS.
- Реализовать покупку, отмену пользователем, pending, восстановление и управление подпиской Apple. Цены, валюта и eligibility берутся из магазина.
- Проверять транзакции на сервере; обрабатывать App Store Server Notifications, повторную доставку, продление, истечение, grace period, возврат и отзыв.
- Связать purchase с аккаунтом через устойчивый идентификатор; защитить от выдачи одной покупки нескольким аккаунтам. Продумать объединение статусов Stripe и Apple и предупреждение о действующей подписке.
- Показывать срок, цену, условия продления, ссылки на privacy/terms и восстановление покупок. Удаление аккаунта не должно ошибочно обещать автоматическую отмену Apple-подписки.

Готово, когда: sandbox-покупка, восстановление после переустановки, возврат и истечение корректно меняют доступ на сервере; клиент не может выдать себе Plus.

## 4. Довести поведение на iPhone

- Проверить safe area, клавиатуру, нижнюю навигацию, маленькие экраны, масштаб текста и VoiceOver.
- Проверить звук после первого касания, фонового режима и прерываний; поддержать системное управление звуком.
- Заменить зависимость напоминаний от Web Notification/service worker на нативные уведомления. Для первого релиза выбрать локальные напоминания либо APNs/FCM transport; отказ в разрешении не мешает урокам.
- Проверить Share, внешние ссылки, возврат из системного браузера, reset-password и referral links. Сейчас referral URL строится из `window.location.origin` — в native нужен публичный HTTPS-домен.
- Обработать offline, повторные запросы и resume без потери ответов и прогресса. Не обещать доступ к ещё не загруженным урокам без сети.
- Ограничить iOS UI ученическим потоком; проверить реальную полезность приложения и соответствие minimum functionality.

Готово, когда: весь ученический сценарий проходит на физическом iPhone, включая потерю сети и уход в фон.

## 5. Privacy и материалы магазина

- Провести инвентаризацию данных и SDK: аккаунт, учебный прогресс, активность, Firebase, Vercel Analytics, Meta Pixel и серверные conversions.
- Предлагаемый вариант для v1: отключить рекламный Meta tracking в native, включая связанные серверные события. Если tracking сохраняется, отдельно реализовать применимые требования ATT; веб-cookie consent не считать заменой ATT.
- Подготовить App Privacy, privacy manifests и Required Reason API declarations по фактическим зависимостям; проверить итоговый архив и исключить лишние разрешения.
- Проверить доступные privacy policy, terms и support URL. Подготовить иконку, screenshots из реального приложения, название, описание, ключевые слова, возрастной рейтинг и территории.
- Создать изолированный review-аккаунт с нужным доступом и понятными инструкциями; держать backend доступным во время review.
- Настроить signing, capabilities, version/build number и запись приложения в App Store Connect.

Готово, когда: данные магазина соответствуют реальному поведению, архив проходит validation, а ревьюер имеет доступ к полному сценарию.

## 6. TestFlight и выпуск

- На staging выполнить автоматические тесты, web build, API typecheck и lint; новые интеграционные проверки нужны прежде всего для native session и server-side покупок.
- Собрать подписанный Release archive, загрузить в TestFlight и проверить установку/обновление на физическом устройстве.
- Пройти матрицу: вход/Apple/Google → onboarding → бесплатные уроки → paywall → покупка → восстановление → прогресс → отключение сети → logout/удаление. Проверить отказ в уведомлениях и оплате.
- Провести короткую beta с реальными пользователями, разобрать crashes и блокирующие ошибки, подготовить поддержку.
- Отправить проверенную сборку и метаданные на App Review. Первый выпуск — вручную после одобрения; держать совместимость API со старой веб- и iOS-версией, предусмотреть отключение проблемной функции на сервере.

Готово, когда: App Review одобрен, приложение доступно в выбранных странах и установка из App Store проверена.

## Что потребуется от владельца

На этапах signing, покупок и TestFlight: Apple Developer membership, доступ к нужной Team/App Store Connect, данные продавца и договоры для платных подписок. Пароли и приватные ключи не передавать в чат. Также нужно определить страны первого выпуска, окончательный Bundle ID и коммерческие условия Apple-подписки.

До этих этапов можно выполнить локальную интеграцию, тесты и подготовку материалов. Срок публикации зависит от обнаруженных проблем с native-сессией, покупок и App Review; точную дату до первого работающего iOS-сценария не фиксируем.
